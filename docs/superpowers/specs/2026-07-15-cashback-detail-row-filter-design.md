# Фильтрация строк кешбэка в истории операций

## Проблема

На банковском скриншоте после расходной операции может идти строка категории с начисленным кешбэком, например `Красота +20 ₽` или `Продукты +3 ₽`. Такая строка является детализацией предыдущей покупки, но OCR-парсер может принять её за самостоятельную доходную операцию.

Текущая защита отбрасывает строку только при точном совпадении очищенного текста с известным названием категории. Она не работает для банковских категорий, отсутствующих в справочнике приложения, и для строк с OCR-шумом.

## Решение

`parseBankHistoryRows` должен учитывать контекст предыдущей принятой операции. Небольшая положительная строка, расположенная сразу после расхода, считается детализацией кешбэка, если её текст похож на банковскую категорию. Проверка допускает OCR-шум и поддерживает `Красота` как банковскую категорийную подсказку.

Проверка применяется только к положительным строкам после расхода. Самостоятельные доходы с явным назначением, включая проценты, компенсации, пополнения и входящие переводы, продолжают распознаваться как операции.

## Границы изменения

- Изменяется только frontend OCR-парсер истории операций.
- Backend, сохранение транзакций и review-интерфейс не меняются.
- Не отбрасываются все небольшие положительные суммы без учёта контекста.
- Не добавляется отдельная категория расходов `Красота` в продуктовый справочник.

## Проверка

Регрессионный тест воспроизводит последовательность `Золотое Яблоко -2 000 ₽ / Красота +20 ₽` и `Мясная кухня -344 ₽ / Продукты +3 ₽`. Результат должен содержать только две расходные операции. Существующие тесты самостоятельных доходов и цифровой банковской истории должны остаться зелёными.
